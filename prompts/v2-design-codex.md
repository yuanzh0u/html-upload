### 第一部分：需求评估（放在文档最前面，标题「0. 需求评估」）

逐条给出可执行判断，不要泛泛而谈：

### 第二部分：V2 方案

章节结构参照 DESIGN-v3，至少覆盖：

1. 结论、约束与需求追踪（FR-01…FR-12 → 方案章节的追踪表，缺一不可）
2. 总体架构与关键请求时序（登录、上传、检索、分享访问、撤销分享、管理员操作）
3. 数据模型（新增/变更表：users、documents、friendships、groups、group_members、shares、api_keys；含索引与唯一约束）
4. 权限模型与分享语义（单向好友、群组继承、实时判定、撤销即时生效、无匿名链接）
5. 接口契约（Agent 侧 HTTP + MCP 工具清单；管理端接口；错误码与不泄露存在的策略）
6. API Key 生命周期（一人一把、长期有效、重新生成即失效旧 Key、用户删除即失效）与泄露应对
7. 管理员能力边界（只见元数据、无正文接口、审计留痕）
8. 删除用户的级联删除策略与事务边界
9. 检索设计（标题/标签/摘要/上传时间；单用户 1000 条数据下的实现取向）
10. 清单编排（Agent 可改分类/标签/排序；存储与呈现）
11. 安全设计（空间隔离、XSS 沙箱与不透明源、直接 URL 探测防护、Key 不入日志、CSRF）
12. 从 V1 到 V2 的迁移方案（现有用户、文档、taxonomy、API Key 如何平滑过渡；可否灰度）
13. 分阶段实施建议与每阶段验收（不排期、不报价）
14. 风险与未决项清单
